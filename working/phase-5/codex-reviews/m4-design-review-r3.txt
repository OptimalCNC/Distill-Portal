   366	## Methodology footnote — `color-mix(in srgb, X p%, Y)` semantics
   367	
   368	The `color-mix(in srgb, ...)` recipe per CSS Color L4 §4.1 mixes
   369	two colors in the **nonlinear sRGB color space**. The committed
   370	`wcag_m4.py` at `working/phase-5/designs/m4-transcript/wcag_m4.py`
   371	implements the pipeline:
   372	
   373	1. Converts each oklch color to linear sRGB (via oklab — Björn
   374	   Ottosson's M2 matrix; `wcag_m4.py:58-71`).
   375	2. Converts each linear sRGB triple to nonlinear sRGB via the
   376	   piecewise function in CSS Color L4 §10.4 (`wcag_m4.py:74-79`).
   377	3. Mixes by `p1 * sRGB1_channel + (1 - p1) * sRGB2_channel`
   378	   (`wcag_m4.py:105-118`).
   379	4. Converts the mixed nonlinear sRGB back to linear sRGB
   380	   (`wcag_m4.py:82-86`).
   381	5. Computes relative luminance via WCAG 2.1 §1.4.3
   382	   (`wcag_m4.py:95-96`).
   383	
   384	This pipeline matches Chromium's implementation of `color-mix(in
   385	srgb)`. Mixing directly in linear sRGB (skipping steps 2 + 4) gives
   386	an answer that drifts by ~0.4-0.8 ratio points at the M4 alpha
   387	values (5%, 8%) — exactly the magnitude of the round-2 hand-derived
   388	drift codex caught. The script's nonlinear-sRGB-then-mix pipeline
   389	is authoritative.

    16	## 1. Brief
    17	
    18	**M4 is the chunk where the right pane finally speaks.** M2a landed
    19	the language (Fraunces, oklch ramp, motion tokens, noise overlay).
    20	M2b landed the chrome (tab strip + minimal header + Metadata + Raw +

    23	become readable text on the screen.
    24	
    25	The Transcript tab is the **default landing surface from M4 onward**
    26	(per Resolved Decision #11): on every fresh selection, the user lands
    27	here unless they were on a different tab when the previous selection
    28	finished. So this surface carries the first-impression weight for
    29	every session click. It must read as quiet, finished, editorial — not
    30	chatty, not chunky, not loud. Six restraints carry the weight:
    31	
    32	1. **Ink-on-paper rhythm.** Reading content lives at 70ch with
    33	   comfortable leading. Messages stack vertically with a
    34	   three-magnitude rhythm: 16 px default between any two adjacent
    35	   messages, 24 px override between adjacent same-kind messages
    36	   (user→user, assistant→assistant, etc.), and 32 px around chapter
    37	   breaks (boundary messages). The scroll surface reads like a printed
    38	   transcript, not a chat log.
    39	
    40	2. **One tint, used surgically.** User messages carry a 5 % accent
    41	   tint over the surface (mirrors the selected-row recipe — same
    42	   recipe, different surface). Assistant messages sit on the bare
    43	   warm-paper surface. The tint differential IS the user/assistant
    44	   discrimination. No avatars. No icons. No labelled rails.
    45	
    46	3. **The chapter break as page furniture.** Boundary messages
    47	   render as a full-width 1 px hairline with a centered Fraunces
    48	   italic small-caps label ("SESSION RESUMED" / "CONVERSATION
    49	   COMPACTED"). 32 px breathing on either side. This is signature
    50	   detail #1 from §Design Language; M4 is the chunk that lands it
    51	   first (M5's Skim view will reuse the recipe verbatim).
    52	
    53	4. **Banners that whisper, not shout.** The truncation banner
    54	   carries a 3 px warn stripe on the inline-start edge plus an 8 %
    55	   warn-tinted background. It does NOT carry an icon, an emoji, or a
    56	   close button. The parse-warnings banner is a `<details>` element
    57	   that disappears entirely when dismissed; warnings re-arrive on
    58	   next session selection per spec.
    59	
    60	5. **Tools fold quietly.** `tool_use` and oversized `tool_result`
    61	   messages collapse behind native `<details>` disclosures with the
    62	   spec's exact summary copy ("Arguments", "Expand (N more bytes)").
    63	   The `<pre>` blocks sit on `--color-surface-raised` so they read
    64	   as machinery — distinct from the body prose without being loud.
    65	
    66	6. **Timestamps as marginalia.** The relative-time label is the
    67	   visible affordance; the absolute ISO is the `dateTime` attribute
    68	   plus the `title` hover tooltip. Null timestamps render as a
    69	   single em-dash. Timestamps NEVER appear on boundary messages —
    70	   the chapter break is editorial, not chronological.
    71	
    72	The aesthetic vision: a returning user opens a session, sees the
    73	right pane fade in, and reads the conversation the way they would
    74	read a printed memo. The left rail of subtle accent tint marks user
    75	turns. Tools collapse inside disclosures — present but not
    76	demanding. The chapter break, when it appears, slows the eye for a
    77	breath. Banners advise without interrupting. There is no chrome
    78	between the user and the words.

   114	## 2. Component tree
   115	
   116	The TranscriptView tree is a single state-discriminator at the top
   117	followed by a flat per-kind render. No nested feature components, no
   118	context, no hooks beyond the one `useParsedSession` call already
   119	contracted by M3b.
   120	
   121	```text
   122	<TranscriptView row={row} now={now}>
   123	  ├── (state === "idle") → <p class="transcript-empty">…</p>
   124	  ├── (state === "no_raw") → <p class="transcript-not-imported">…</p>
   125	  ├── (state === "loading") → <p class="transcript-loading">…</p>
   126	  ├── (state === "error") → <p class="transcript-error">…</p>
   127	  │                          + <button class="transcript-retry">Retry</button>
   128	  └── (state === "success" | "truncated")
   129	       └── <TranscriptBody parsed={…} now={…} truncated={…}>
   130	            ├── (truncated) → <TruncationBanner />
   131	            ├── (warnings.length > 0 && !dismissed) → <ParseWarningsBanner />
   132	            └── <ol class="transcript-stream">
   133	                 ├── (messages.length === 0) → <li class="transcript-empty-stream">…</li>
   134	                 └── messages.map(msg => <MessageRow msg={msg} now={now} />)
   135	                      ├── kind="user"        → <UserMessage />
   136	                      ├── kind="assistant"   → <AssistantMessage />
   137	                      ├── kind="tool_use"    → <ToolUseMessage />
   138	                      ├── kind="tool_result" → <ToolResultMessage />
   139	                      ├── kind="system"      → <SystemMessage />
   140	                      ├── kind="boundary"    → <BoundaryMessage />
   141	                      └── kind="unknown"     → <UnknownMessage />
   142	```

   169	### 2.3 The keep-mounted contract
   170	
   171	TranscriptView's React subtree carries **no `key=` on its root**. Per
   172	M2b's Resolved Decision #12 (spec lines 650-658), tab switches must
   173	NOT remount the panel content. The only natural state-reset point is
   174	a `selectedRowKey` change, which is handled at the SessionView layer
   175	via `<SessionView key={selectedRowKey}>`.
   176	
   177	Component-local state that persists across tab switches:
   178	
   179	- `warningsBannerDismissed` (`useState<boolean>`).
   180	- Native `<details>` open/closed state (browser-managed; survives
   181	  reparenting because the element instance is stable).
   182	- Scroll position (browser-managed; survives `display: none` toggles).
   183	
   184	Defensive belt-and-suspenders:
   185	
   186	```tsx
   187	useEffect(() => setDismissed(false), [row.rowKey]);
   188	```
   189	
   190	This `useEffect` resets the dismissed banner when the row changes,
   191	even though the parent's `key={selectedRowKey}` already destroys and
   192	recreates the component on selection change. The defensive reset
   193	matches the SessionView pattern at `SessionView.tsx:223-226`.
   194	
   195	The only place a React `key=` is used inside TranscriptView is on
   196	`<MessageRow key={msg.messageIndex} />` — that's content keying, not
   197	tab keying, and is required for stable React reconciliation.

   420	### 3.7 `unknown` — fallback line
   421	
   422	Spec anchor: `working/phase-5.md:711`.
   423	
   424	> "muted single line 'Unrecognized line: {first 80 chars}…' in
   425	> `--font-mono` `--text-xs` — fallback for unparseable shapes."
   426	
   427	**Container.** `<p class="msg msg-unknown">`. NO background, NO
   428	border. `--font-mono --text-xs --color-ink-muted`. `font-style: italic`.
   429	`max-inline-size: var(--measure)`. `word-break: break-all`.
   430	
   431	**Composition.** Literal "Unrecognized line: " prefix in chrome font,
   432	then `msg.text.slice(0, 80)` in mono, then (conditionally) a single
   433	ellipsis character U+2026 (NOT three dots). The prefix fixed at chrome
   434	to read as operator commentary; the slice in mono to read as raw
   435	payload.
   436	
   437	**Ellipsis rule (IMPORTANT-4 resolution).** Spec line 711 says
   438	"Unrecognized line: {first 80 chars}…". The trailing ellipsis is
   439	appended by the renderer **only when the original text was actually
   440	truncated** — i.e., only when the input length exceeds 80 chars.
   441	Specifically:
   442	
   443	- If `msg.text.length > 80`: slice to 80 chars THEN append U+2026
   444	  ellipsis. Output is `{slice (≤ 80 chars)}…`.
   445	- If `msg.text.length <= 80`: use `msg.text` as-is, NO trailing
   446	  ellipsis. Output is `{msg.text}` verbatim.
   447	- The U+2026 ellipsis character (`…`) is **appended by the
   448	  renderer**, not part of the slice. If the original payload already
   449	  contains a U+2026 at byte 75, slicing the first 80 chars preserves
   450	  that embedded ellipsis, then the renderer appends ONE additional
   451	  trailing U+2026, yielding `{slice including the embedded U+2026}…`
   452	  (two ellipses visible — one inside the slice, one trailing).
   453	
   454	```tsx
   455	function unknownLine(text: string): string {
   456	  if (text.length > 80) return text.slice(0, 80) + "…";
   457	  return text;
   458	}
   459	```
   460	
   461	Implementation note: the chrome/mono mix inside a single `<p>`
   462	requires inner spans, e.g. `<span class="msg-unknown-prefix">Unrecognized

   464	the trailing `…` is conditional per the rule above). Both spans
   465	inherit the muted color and italic style; the spans only re-declare
   466	`font-family` to flip the typeface.

   477	## 4. Spacing rhythm
   478	
   479	Spec anchor: `working/phase-5.md:701`.
   480	
   481	> "Reading-content layout: max-inline-size 70ch, generous vertical
   482	> rhythm (16 px between messages, 24 px between adjacent same-kind
   483	> messages with a kind-change gap of 32 px)."
   484	
   485	The rhythm has three magnitudes, each anchored to an existing token:
   486	
   487	| Distance | Token              | Resolved | Used between                                                              |
   488	|----------|--------------------|----------|---------------------------------------------------------------------------|
   489	| 16 px    | `var(--space-4)`   | `1rem`   | DEFAULT — any two adjacent messages where no other override fires (e.g. user → assistant, assistant → tool_use) |
   490	| 24 px    | `var(--space-6)`   | `1.5rem` | Same-kind override: adjacent same-kind messages (user → user, assistant → assistant, tool_use → tool_use, etc.) |
   491	| 32 px    | `var(--space-8)`   | `2rem`   | Boundary breathing — above AND below every `.msg-boundary` (overrides both the 16 px default and the 24 px override) |
   492	
   493	### 4.1 The CSS expression
   494	
   495	The rhythm uses adjacent-sibling selectors on the wrapping `<ol>`:
   496	
   497	```css
   498	/* Default: 16 px between any two adjacent messages */
   499	.transcript-stream > .msg + .msg {
   500	  margin-top: var(--space-4);
   501	}
   502	
   503	/* 24 px between adjacent same-kind messages */
   504	.transcript-stream > .msg-user      + .msg-user      { margin-top: var(--space-6); }
   505	.transcript-stream > .msg-assistant + .msg-assistant { margin-top: var(--space-6); }
   506	.transcript-stream > .msg-tool-use  + .msg-tool-use  { margin-top: var(--space-6); }
   507	.transcript-stream > .msg-tool-result + .msg-tool-result { margin-top: var(--space-6); }
   508	.transcript-stream > .msg-system    + .msg-system    { margin-top: var(--space-6); }
   509	
   510	/* 32 px around boundary messages */
   511	.transcript-stream > .msg-boundary,
   512	.transcript-stream > .msg-boundary + .msg {
   513	  margin-top: var(--space-8);
   514	}
   515	.transcript-stream > .msg + .msg-boundary {
   516	  margin-top: var(--space-8);
   517	}
   518	```
   519	
   520	The CSS implements a **three-magnitude rule** verbatim:
   521	
   522	1. **16 px (default)** — every adjacent message pair, applied via
   523	   `.msg + .msg { margin-top: var(--space-4); }`. This is the floor
   524	   that fires for adjacent-different-kind pairs (e.g. user → assistant,
   525	   assistant → tool_use, tool_result → assistant). NOT a "kind-change"
   526	   rule — it is the default between any two messages where no other
   527	   override fires.
   528	2. **24 px (same-kind override)** — adjacent-sibling selectors per
   529	   kind (`.msg-user + .msg-user`, `.msg-assistant + .msg-assistant`,
   530	   `.msg-tool-use + .msg-tool-use`, etc.). These tighten same-kind
   531	   stacks because they group editorially.
   532	3. **32 px (boundary breathing)** — applied above AND below every
   533	   `.msg-boundary`. This is the chapter-break breathing room; it
   534	   overrides both the 16 px default and the 24 px same-kind rule.
   535	
   536	**Final decision**: M4 ships this three-magnitude rule. Spec line 701's
   537	"kind-change gap of 32 px" is interpreted as a ceiling that applies
   538	specifically to **boundary** transitions (which ARE kind-changes by
   539	construction — boundary is the only kind that triggers 32 px). The
   540	16 px default IS the kind-change rhythm for non-boundary pairs; the
   541	24 px override IS the same-kind rhythm. There is no separate
   542	"kind-change = 32 px" rule for non-boundary adjacencies — that
   543	reading would be inconsistent with the CSS the prototype ships.
   544	
   545	The previous round-1 designer interpretation that "kind-change = 32 px
   546	on every adjacent-different-kind pair" is REJECTED. Wireframes and
   547	copy are aligned to the CSS in round 2 (BLOCKING-1 resolution).
   548	
   549	### 4.2 Reading measure
   550	
   551	Every text-bearing message panel carries `max-inline-size:
   552	var(--measure)` (= 70ch). Tool messages (which contain `<pre>` blocks
   553	with their own `overflow-x: auto`) also cap at 70ch — the `<pre>`
   554	internal scroll handles long lines without forcing the panel wider.
   555	
   556	The boundary message is the ONE exception: its grid expands to the
   557	full inline-size of the `transcript-stream` container so the rules
   558	visually reach edge-to-edge of the reading column. The reading column
   559	itself is constrained to `var(--measure)` at the `.transcript-stream`
   560	level.
   561	
   562	### 4.3 First and last spacing
   563	
   564	The `transcript-stream` wrapper carries `padding-block: var(--space-6)
   565	0` (top inset only) so the first message is not flush against the
   566	tab strip's hairline. No bottom inset — the panel's natural bottom
   567	edge handles the cutoff. Banners (when present) sit ABOVE the stream's
   568	top inset, with their own `margin-bottom: var(--space-6)` to separate
   569	them from the first message.

   573	## 5. Timestamp display
   574	
   575	Spec anchor: `working/phase-5.md:713`.
   576	
   577	> "Each message panel carries a timestamp display: relative time as
   578	> visible label (`relativeTimeFrom(now, msg.timestamp)`), absolute ISO
   579	> via `<time dateTime='…'>` and on `title=` hover. Timestamps with
   580	> `null` value render as '—' (preserved from Phase 4 contract)."
   581	
   582	### 5.1 The `<time>` element
   583	
   584	```tsx
   585	function MessageTime({ iso, now }: { iso: string | null; now: string }) {
   586	  if (iso === null) {
   587	    return <time>—</time>;
   588	  }
   589	  const rel = relativeTimeFrom(now, iso);
   590	  return <time dateTime={iso} title={iso}>{rel}</time>;
   591	}
   592	```
   593	
   594	- Visible text: the relative-time label (e.g. "3 minutes ago", "2
   595	  days ago"). Computed via `relativeTimeFrom(now, iso)` which is
   596	  already wired in Phase 4 / M2b.
   597	- `dateTime={iso}` attribute: the absolute ISO 8601 string.
   598	  Machine-readable for browser tooltips, copy-paste, screen readers,
   599	  and search-engine indexing.
   600	- `title={iso}` attribute: the absolute ISO string also surfaced on
   601	  hover (browser default tooltip).
   602	- Null: a single em-dash character (U+2014) inside a `<time>` with no
   603	  `dateTime` attribute. Rendering still uses the `<time>` shell so
   604	  the surrounding CSS (which targets `time` with the muted-italic
   605	  rule) treats null timestamps consistently.
   606	
   607	### 5.2 No timestamp on boundary messages
   608	
   609	Per Q7 in m4-plan §5, boundary messages do NOT carry a `<time>`. The
   610	chapter-break treatment is editorial. The user message that follows
   611	the boundary carries its own timestamp, giving the chronological
   612	signal where the user expects it.
   613	
   614	### 5.3 Where timestamps appear
   615	
   616	Timestamps render INSIDE the attribution row (`.msg-attr`) for
   617	`user`, `assistant`, `tool_use`, `tool_result`. They do NOT render on
   618	`system` (single-line muted prose; timestamp would clutter), `boundary`
   619	(editorial), or `unknown` (fallback diagnostic; no useful chronology).

   625	Spec anchor: `working/phase-5.md:715`.
   626	
   627	> "If `parsed.truncated`, a small banner at the top of the Transcript:

   629	> anchor in the session header to inspect the full payload.' Banner

   632	
   633	### 6.1 Copy (verbatim from spec line 715)
   634	
   635	> Truncated at 5 MB — full payload not parsed. Use the **Open raw**
   636	> anchor in the session header to inspect the full payload.
   637	
   638	The "Open raw" word is bolded text only — there is NO anchor element
   639	embedded inside the banner. The banner copy is a **reference** to the
   640	"Open raw" anchor that lives in the session header (see §6.1.1 below).
   641	
   642	The banner copy is now spec-verbatim because §6.1.1 lands the
   643	session-header anchor in the same M4 chunk; the dangling-reference

   646	```tsx
   647	<div className="transcript-banner transcript-banner-truncation" role="status">

   649	</div>
   650	```
   651	
   652	### 6.1.1 Session header expansion in M4 (BLOCKING-2 resolution)
   653	
   654	Spec line 626 enumerates "Open raw" as a session-header element. M2b
   655	shipped a minimal header without it (deferred). The truncation banner
   656	copy at spec line 715 is load-bearing — it points users to a
   657	session-header anchor that does NOT yet exist. Round-2 coordinator
   658	resolution: M4 scope EXPANDS to include landing the "Open raw" anchor
   659	in the session header.
   660	
   661	**Where it lands.** `apps/frontend/src/features/sessions/SessionView.tsx`
   662	header. The header currently renders title + tool badge + status pill
   663	+ conflict badge from M2b; M4 appends "Open raw" to the right-side
   664	action group, AFTER the conflict badge.
   665	
   666	**Visibility rule.** Visible only when `row.storedSessionUid !== null`
   667	(matches `SessionMetadata.tsx`'s "View raw" anchor visibility rule
   668	from M2b). When the row is source-only (`storedSessionUid === null`),
   669	the anchor is omitted entirely — it would 404 anyway, and the
   670	truncation banner only fires for parsed sessions which by definition
   671	have a stored UID.
   672	
   673	**Anchor copy.** `Open raw` — verbatim per spec line 626. NOT "View
   674	raw" (which is the Metadata-tab precedent); the spec uses "Open raw"
   675	specifically for the header position to differentiate from the
   676	Metadata tab's variant.
   677	
   678	**Anchor URL.** `/api/v1/sessions/${row.storedSessionUid}/raw` via the
   679	existing `RAW_SESSION_PATH` builder in `apps/frontend/src/lib/api.ts`.
   680	Reuses the same path as Metadata's "View raw"; the difference is the
   681	copy and the position, not the destination.
   682	
   683	**Anchor attributes.** `target="_blank"` + `rel="noreferrer"` —
   684	matches the Phase 4 pattern at `SessionMetadata.tsx`. No `download`
   685	attribute (the user inspects the raw payload in a new tab; downloading
   686	is opt-in via the browser's UI).
   687	
   688	**Position.** Right-side action group of the session header, AFTER the
   689	conflict badge. The order top-to-bottom (in the flex row): title (left
   690	flex-grow), tool badge (left), then on the right: status pill →
   691	conflict badge → "Open raw".
   692	
   693	**Typography.** `--font-chrome --text-sm`. Color `--color-accent` (link
   694	styling per the existing "View raw" precedent at `SessionMetadata.tsx`).
   695	Hover: underline. Focus-visible: 2 px accent outline + 2 px offset.
   696	
   697	**State variants.** Hidden when `state === "no_raw"` (anchor would 404
   698	since `storedSessionUid` is null). Visible otherwise (`success`,
   699	`truncated`, `loading`, `error`, `idle`). The anchor's position in the
   700	header is structural — it does not jump around as state changes.
   701	
   702	**Truncation banner relationship.** When `state === "truncated"` the
   703	"Open raw" anchor in the header IS the destination the banner copy
   704	points to. They co-render: banner in the transcript top, anchor in
   705	the session header. The user follows the prose hint "Use the Open
   706	raw anchor in the session header" → eye flies up to the header →
   707	clicks the anchor → opens raw payload in new tab.
   708	
   709	**Developer task at M4 implementation time** (documented here because
   710	m4-plan.md is frozen for this design loop): the developer's modified
   711	files list at m4-plan §3 must be expanded to include
   712	`apps/frontend/src/features/sessions/SessionView.tsx` (for the header
   713	anchor) and `apps/frontend/src/features/sessions/SessionView.test.tsx`
   714	(for a regression test that asserts the anchor renders when
   715	`storedSessionUid !== null` and is omitted when null). The CSS
   716	modifications belong in `SessionView.css` (existing per-component
   717	sibling). Reuse existing tokens; no new token additions for this
   718	expansion.
   719	
   720	### 6.2 Visual recipe
   721	
   722	- **Container.** `<div class="transcript-banner transcript-banner-truncation"
   723	  role="status">`. The `role="status"` makes screen readers announce
   724	  the banner without interrupting; assistive tech treats it as a
   725	  polite live region.
   726	- **Background.** `color-mix(in srgb, var(--color-warn) 8%, var(--color-surface))`.
   727	  A warm wash; reads as a soft warn tint without screaming.
   728	- **Inline-start stripe.** `border-inline-start: 3px solid var(--color-warn)`.
   729	  3 px is the SC 1.4.11 non-text bar; the warn color holds against
   730	  surface (pair B02 in colors.md).
   731	- **Padding.** `var(--space-3) var(--space-4)` (12 px / 16 px).
   732	- **Border-radius.** `var(--radius-sm)`.
   733	- **Typography.** `--font-chrome --text-sm --color-ink`. Body weight.
   734	  `<strong>Open raw</strong>` carries `font-weight: 600` (the chrome
   735	  bold weight).
   736	- **Margin-bottom.** `var(--space-6)` (24 px) to separate from the
   737	  warnings banner (if both present) or the first message.
   738	
   739	### 6.3 Motion
   740	
   741	- **Property.** `opacity` ONLY (NOT `background-color`, NOT `transform`).
   742	- **Duration.** `var(--motion-base)` (120 ms).
   743	- **Easing.** `var(--ease-out)`.
   744	- **Trigger.** `parsed.truncated` becomes true → component mounts.
   745	- **Implementation.** `animation: transcript-banner-fade
   746	  var(--motion-base) var(--ease-out) both;` where:
   747	
   748	  ```css
   749	  @keyframes transcript-banner-fade {
   750	    from { opacity: 0; }
   751	    to   { opacity: 1; }
   752	  }
   753	  ```
   754	
   755	The `both` fill mode keeps opacity at 1 after the animation completes
   756	(matches M2b's tab-fade-in pattern). Reduced-motion zeroes the
   757	duration via the global rule.
   758	
   759	### 6.4 What the banner does NOT do
   760	
   761	- It does NOT carry an icon. The warm tint + the inline-start stripe
   762	  + the prose are enough.
   763	- It does NOT carry a close button. The truncation is a state of the
   764	  parsed session; dismissing the banner without dismissing the
   765	  underlying truth would be misleading. (Contrast with the
   766	  parse-warnings banner, which IS dismissible because warnings are
   767	  diagnostic noise.)
   768	- It does NOT animate `background-color` or `transform`. Codex M2b
   769	  r1 #2 caught a `background-color` transition on a non-enumerated
   770	  surface; M4's banner uses opacity-only entrance to comply with the
   771	  motion budget.

   948	## 9. Long tool_result collapse
   949	
   950	Spec anchor: `working/phase-5.md:708`.
   951	
   952	### 9.1 Threshold
   953	
   954	`TOOL_RESULT_OVERFLOW_BYTES = 2048` bytes. Discriminator:
   955	`msg.bytes > 2048` (NOT `msg.text.length`; per Q2 in m4-plan §5).
   956	
   957	### 9.2 Split-point algorithm
   958	
   959	```ts
   960	function splitToolResult(text: string): { head: string; tail: string | null } {
   961	  const enc = new TextEncoder();
   962	  const dec = new TextDecoder();
   963	  const all = enc.encode(text);
   964	  if (all.length <= 2048) return { head: text, tail: null };
   965	  // Walk back from byte 2048 to a UTF-8 codepoint boundary.
   966	  // UTF-8 continuation bytes start with bits 10xxxxxx.
   967	  let cut = 2048;
   968	  while (cut > 0 && (all[cut] & 0xC0) === 0x80) cut--;
   969	  const head = dec.decode(all.slice(0, cut));
   970	  const tail = dec.decode(all.slice(cut));
   971	  return { head, tail };
   972	}
   973	```
   974	
   975	Test obligations (m4-plan §8):
   976	- 2048-byte body: no overflow.
   977	- 2049-byte body: overflow with 1-byte tail.
   978	- Multi-byte UTF-8 (emoji, CJK) at the cut point: cut walks back to
   979	  a clean codepoint boundary; head + tail concatenate to the original.
   980	
   981	### 9.3 Disclosure
   982	
   983	Wrapper: `<details class="msg-tool-disclosure msg-tool-overflow">`.
   984	Summary: `Expand ({Nmore} more bytes)` where `Nmore = msg.bytes - 2048`.

  1127	### 12.1 Roles and landmarks
  1128	
  1129	- `<section class="transcript-body" aria-label="Session transcript">`:

  1132	- `<ol class="transcript-stream">`: implicit `role="list"`. Each

  1134	  carries `role="separator"` directly (no nested `<div>`) per
  1135	  Q-DESIGN-3 round-2 resolution in §12.2 — the flat shape matches
  1136	  the prototype and wireframes.
  1137	- `<article>` wrappers on user/assistant/tool messages: implicit
  1138	  `role="article"`. Screen readers announce each turn as a discrete
  1139	  unit.
  1140	- `<header>` inside each message: implicit `role="banner"` for the
  1141	  first one in the document; subsequent are unnamed but still

  1146	### 12.2 Q-DESIGN-3: `<ol>` containing separators — RESOLVED (round 2)
  1147	
  1148	The spec calls for `role="separator"` on boundary messages. The
  1149	wrapping container is `<ol>`, which expects only `<li>` children.
  1150	Round-1 designer flagged two options (Option A: `<li>` wrapper with
  1151	internal `<div role="separator">`; Option B: switch container to
  1152	`<div>` and lose the list count).
  1153	
  1154	**Coordinator resolution (round 2): the flat shape on the `<li>`
  1155	itself.** The boundary message ships as
  1156	`<li class="msg msg-boundary" role="separator" aria-orientation="horizontal">`.
  1157	The `<li>` element carries `role="separator"` directly — no nested
  1158	`<div>`. This is valid: ARIA allows overriding the implicit role of
  1159	`<li>` (which is `listitem`) with `role="separator"` because the
  1160	boundary is semantically a separator, not a list item. The visual
  1161	content (rule + label + rule via CSS Grid) lives directly inside the
  1162	`<li>`.
  1163	
  1164	Screen readers announce the element as a separator with the label
  1165	text ("separator: SESSION RESUMED" or "separator: CONVERSATION
  1166	COMPACTED"), bypassing the list-item count. Adjacent message `<li>`s
  1167	on either side keep their listitem role and announce normally
  1168	("message 47 of 312"). The boundary is not counted in the listitem
  1169	sequence — which matches the editorial intent (chapter break is
  1170	between turns, not a turn itself).
  1171	
  1172	This is the shape the prototype already ships at
  1173	`prototype.html:991-995` and the wireframe at
  1174	`wireframes/04-boundary-mid-stream.txt:67-71`. Round-1 design.md drift
  1175	to a nested-`<div>` shape is corrected in round 2.

  1193	### 12.4 `tabIndex={0}` on the active tabpanel — IMPORTANT-5 resolution
  1194	
  1195	M2b r1 #5 caught Skim/Transcript placeholder tabpanels lacking
  1196	`tabIndex={0}`. The Tabs primitive in `apps/frontend/src/components/`
  1197	applies `tabIndex={isActive && (id === "skim" || id === "transcript"
  1198	|| id === "raw") ? 0 : undefined}` per the M2b motion.md §"Surface 2"
  1199	recipe. M4's tabpanel inherits this — its `tabIndex={0}` survives even
  1200	though the panel now has focusable children (the `<summary>` elements,
  1201	the Retry button, the Dismiss button).
  1202	
  1203	**Round-2 resolution (IMPORTANT-5).** Per WAI-ARIA APG, a tabpanel
  1204	WITH focusable descendants does NOT strictly need `tabIndex={0}`.
  1205	M4's TranscriptView has focusable children (Retry button, Dismiss
  1206	button, `<details>` summaries on tool messages and the parse-warnings
  1207	banner), so APG would technically allow stripping `tabIndex={0}` from
  1208	the active Transcript tabpanel.
  1209	
  1210	**Coordinator decision: keep `tabIndex={0}` unconditional on the
  1211	active Transcript tabpanel for consistency with M2b's Option-A,
  1212	even though APG would technically allow stripping it.** Rationale:
  1213	the cost of an extra tab stop is one extra Tab keypress (the user
  1214	tabs from the tab strip into the tabpanel, then again to reach the
  1215	first focusable child); the benefit is **rule simplicity** — every
  1216	active tabpanel gets `tabIndex={0}` regardless of whether it has
  1217	focusable descendants, with no per-tab logic. Codex M2b r1 #5 +
  1218	r2 #1 precedent verified.
  1219	
  1220	The rule M4 ships, restated: "Every active tabpanel of the
  1221	distill-portal Tabs primitive carries `tabIndex={0}`. No exceptions
  1222	based on whether the panel has focusable descendants." This rule
  1223	survives M4's expansion of TranscriptView from a placeholder (no
  1224	focusable descendants) to a full transcript (multiple focusable
  1225	descendants). Cross-reference: M2b Resolved Decision Option-A.

  1306

  1316	3. **Nested backticks inside a fenced block.** Inner ` ` ` ` pairs
  1317	   render as literal characters — the `<pre>` content is opaque to
  1318	   inline-code detection. The outer fence delimits the boundary; once
  1319	   inside the `<pre>`, no further inline-code rewriting fires.

  1328	   fence does not need a separate cue.
  1329	6. **Single-backtick spanning a newline.** Renders as plain text
  1330	   (the inline-code detector requires both backticks on the same
  1331	   line). Documented; not a warning.

    22	| 2   | **Disclosure (`<details>`) expand/collapse** | `block-size` (via `interpolate-size: allow-keywords`) | `--motion-disclosure` (200 ms) | `--ease-in-out`         | user toggle on `<summary>`                        | Native `<details>` element + global CSS rule on `details > *` |
    23	
    24	## M4's INSTANT (non-animated) surfaces
    25	
    26	These M4 surfaces undergo state changes with NO animation /
    27	transition. The change applies on the next paint without
    28	interpolation:
    29	
    30	| #   | Surface                                  | State change                                | Trigger              |
    31	|-----|------------------------------------------|---------------------------------------------|----------------------|
    32	| 3   | Message panel mount                      | none — panels appear at full opacity         | first paint per session |
    33	| 4   | Tool `<pre>` block scroll                | native scroll                                | user scroll          |
    34	| 5   | Parse-warnings banner mount              | none — banner appears at full opacity        | `warnings.length > 0` |
    35	| 6   | Dismiss button hover                     | border-color swap (instant)                  | pointer enter        |
    36	| 7   | Retry button hover                       | border-color swap (instant)                  | pointer enter        |
    37	| 8   | tool_result "Expand" summary hover       | `text-decoration: underline` swap (instant)  | pointer enter        |
    38	| 9   | `<summary>` focus-visible                | outline appears                              | focus arrives        |
    39	| 10  | Code-fence segment render                | none — `<pre>` / `<code>` swap is structural | first paint          |
    40	
    41	Why instant rather than animated: `color`, `border-color`,
    42	`text-decoration`, and hover `background-color` on these surfaces
    43	are **NOT** in the spec's frozen motion budget at
    44	`working/phase-5.md:84-95`. The budget is load-bearing per spec
    45	line 1100; adding animations on unlisted surfaces requires a
    46	coordinator waiver, which M4 does not seek. Instant state changes
    47	still feel responsive at 60 Hz; the animated surfaces (#1, #2)
    48	carry the chunk's animation budget.

    50	## Idiom details
    51	
    52	### Surface 1 — Truncation banner appearance
    53	
    54	CSS `@keyframes` on `.transcript-banner-truncation`. The banner is
    55	mounted by the React renderer when `state === "truncated"`; the
    56	animation fires automatically on first paint:
    57	
    58	```css
    59	.transcript-banner-truncation {
    60	  /* Static visual recipe — colors and layout, no animation. */
    61	  background: color-mix(in srgb, var(--color-warn) 8%, var(--color-surface));
    62	  border-inline-start: 3px solid var(--color-warn);
    63	  border-radius: var(--radius-sm);
    64	  padding: var(--space-3) var(--space-4);
    65	  color: var(--color-ink);
    66	  font: var(--text-sm) / var(--leading-comfortable) var(--font-chrome);
    67	  margin-block-end: var(--space-6);
    68	
    69	  /* Animation — opacity ONLY. */
    70	  animation: transcript-banner-fade var(--motion-base) var(--ease-out) both;
    71	}
    72	
    73	@keyframes transcript-banner-fade {
    74	  from { opacity: 0; }
    75	  to   { opacity: 1; }
    76	}
    77	```
    78	
    79	The `animation-fill-mode: both` keeps opacity at 1 after the keyframe
    80	completes (matches M2b's `tab-fade-in` pattern at `SessionView.css`).
    81	On the FIRST mount of `<TruncationBanner>` (e.g. when state
    82	transitions `loading → truncated`), the keyframe fires; on subsequent
    83	re-renders inside the same mount, the property string doesn't change
    84	and the keyframe doesn't re-fire. This is correct: the banner appears
    85	once per truncation.
    86	
    87	**The animation explicitly targets `opacity` and ONLY `opacity`.**
    88	The static visual recipe (background, border, padding, color) is set
    89	at component mount via the static `.transcript-banner-truncation`
    90	selectors above; the static colors are NOT interpolated in.

    92	### Surface 2 — Disclosure (`<details>`) expand/collapse
    93	
    94	Native `<details>` element + a global CSS rule already in place from
    95	M2b:
    96	
    97	```css
    98	/* Lives in apps/frontend/src/styles/global.css (M2b authorization) */
    99	@supports (interpolate-size: allow-keywords) {
   100	  :root {
   101	    interpolate-size: allow-keywords;
   102	  }
   103	}
   104	
   105	details > *:not(summary) {
   106	  /* The disclosure animation: 200 ms ease-in-out on block-size.
   107	   * Per the documented exemption (spec line 88), this is the ONLY
   108	   * layout-touching animation in Phase 5. */
   109	  transition: block-size var(--motion-disclosure) var(--ease-in-out);
   110	}
   111	```
   112	
   113	M4 reuses this rule for three surfaces:
   114	- `tool_use` "Arguments" disclosure.
   115	- `tool_result` "Expand ({Nmore} more bytes)" overflow disclosure.
   116	- Parse-warnings banner `<details>` element.
   117	
   118	If `interpolate-size` is unavailable, the `<details>` snaps without
   119	animation. Acceptable per spec line 124 fallback. M4 does NOT
   120	fallback-test (the M2b suite already covers this).
   121	
   122	**The transition explicitly targets `block-size` and ONLY `block-size`.**
   123	No other property is interpolated during expand/collapse. Open/closed
   124	state itself is browser-managed (the `[open]` attribute toggles
   125	internally; React doesn't drive it).

   127	## PROHIBITED properties — what M4 must NOT animate
   128	
   129	This section is the codex defense. Every property listed below was a
   130	codex blocking finding in M2b round 1 or earlier; M4 must not regress.
   131	
   132	### Properties FORBIDDEN on ALL M4 surfaces
   133	
   134	These properties are forbidden per the §Motion budget + §Performance
   135	budget enumeration in spec lines 84-128. M4 must NOT have ANY CSS
   136	declarations matching:
   137	
   138	- `transition: color …`
   139	- `transition: border-color …`
   140	- `transition: width …`
   141	- `transition: height …`
   142	- `transition: top …`
   143	- `transition: padding …`
   144	- `transition: margin …`
   145	- `transition: font-size …`
   146	- `transition: letter-spacing …`
   147	- `transition: line-height …`
   148	
   149	Audit: `rg -n 'transition: (color|border-color|width|height|top|padding|margin|font-size|letter-spacing|line-height)' apps/frontend/src/features/sessions/TranscriptView.css` must return zero matches.
   150	
   151	### Properties FORBIDDEN on message panels
   152	
   153	These properties may animate elsewhere in Phase 5 (e.g. row hover,
   154	selected row tint, deep-link pulse) but NOT on message panels:
   155	
   156	- `transition: background-color` on `.msg`, `.msg-user`, `.msg-assistant`,
   157	  `.msg-tool-use`, `.msg-tool-result`, `.msg-system`, `.msg-boundary`,
   158	  `.msg-unknown`. The user/assistant tint differential is STATIC
   159	  (color-mix() resolved at mount); no transition on tint change
   160	  because tint doesn't change within a single render. If the user
   161	  toggles between two messages, that's a render of two distinct
   162	  panels, not a tint transition.
   163	- `transform` on `.msg*` selectors. Messages do not slide, scale,
   164	  rotate, or skew. They appear at their final layout position.
   165	
   166	Audit: `rg -nE '\.msg.* (transition|transform)' apps/frontend/src/features/sessions/TranscriptView.css` should match only the global `transform-origin` declarations (none expected) — the absence of message-panel transitions/transforms is the verification.
   167	
   168	### Properties FORBIDDEN inside the truncation banner
   169	
   170	The truncation banner authorizes `opacity` ONLY:
   171	
   172	- NO `transition: background-color` on the banner. The 8 % warn-tint
   173	  background is STATIC (resolved at mount via color-mix); it does not
   174	  fade in or shift. The fade is the OPACITY of the entire banner
   175	  layer.
   176	- NO `transform` on the banner. It does not slide or scale.
   177	- NO `border-color` transition on the warn stripe. The stripe color
   178	  is static.
   179	
   180	Codex precedent: M2b r1 #2 caught a `background-color` transition on
   181	the `.session-conflict-badge` that M4's truncation banner deliberately
   182	echoes the design of. M4's banner uses opacity-only entrance to avoid
   183	the same misuse pattern.
   184	
   185	### Properties FORBIDDEN inside parse-warnings banner
   186	
   187	The parse-warnings banner is a `<details>` element with native
   188	disclosure animation (block-size). NO additional motion:
   189	
   190	- NO `transition: background-color` on the banner shell.
   191	- NO `transition: border-color` on the dismiss button.
   192	- NO `transform` on any element.
   193	- NO opacity animation on mount (the banner is not opacity-faded —
   194	  it appears synchronously when `parsed.warnings.length > 0`).
   195	
   196	The disclosure animation is the ONLY motion on this surface; it
   197	inherits from the global `details > *` rule and adds nothing M4-specific.
   198	
   199	### Properties FORBIDDEN on disclosure summaries
   200	
   201	The `<summary>` elements (Arguments, Expand, parse-warnings):
   202	
   203	- NO `transition` on `color`, `border-color`, `background-color`,
   204	  `text-decoration`. Hover state changes are INSTANT.
   205	- NO `transform` rotation on the disclosure marker. The native
   206	  triangle-rotation animation provided by the browser is NOT
   207	  customized; M4 does not override it.
   208	
   209	### Properties FORBIDDEN on Retry / Dismiss buttons
   210	
   211	Same recipe as M2b's `.raw-retry` and `.metadata-copy-btn`:
   212	
   213	- NO `transition` declarations at all on the buttons.
   214	- Hover and focus-visible states are INSTANT.
   215	
   216	This is the M2b-established pattern; M4 does not deviate.
   217	
   218	### Properties FORBIDDEN on the boundary chapter-break
   219	
   220	The boundary message:
   221	
   222	- NO `transition` or `animation` on the wrapper, the rules, or the
   223	  label. The chapter break is STRUCTURAL — it appears with the rest
   224	  of the transcript stream's first paint (no per-element entrance).
   225	- NO opacity fade on the boundary specifically. The page-turn fade
   226	  at the SessionView outer layer covers the entire stream's mount;
   227	  the boundary inherits that animation as a passive participant.
   228	
   229	### Properties FORBIDDEN on the entire transcript stream
   230	
   231	- NO Skim-style stagger animation on the messages. Spec line 93
   232	  authorizes a stagger ONLY for Skim's first paint (M5); M4's
   233	  transcript stream paints all messages at the same time. The
   234	  page-turn fade at the SessionView layer is the only entrance
   235	  animation that touches M4's content.
