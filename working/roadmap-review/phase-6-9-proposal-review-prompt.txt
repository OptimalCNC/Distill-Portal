## The 4-phase proposal under review

### Phase 6 — Title model + display layer (size: S)

**Goal**: Sessions today display their full `session_key` (e.g., `claude_code:546104ba-031c-46f2-9b24-36b147c6b2f6`) as title. This is ugly and unscannable. Prep the data model for future AI summarization (in Phase 10+).

**Scope**:
- Backend: add `display_title TEXT` (NOT NULL with default) and `summary TEXT NULL` columns to the `sessions` table in raw-session-store. Populate `display_title` on ingest via heuristic (proposed: first user message truncated to 60 chars, with fallback to short session_key tail).
- `ui-api-contracts`: expose `display_title` + `summary` in the `Session` payload.
- Frontend: list panel renders `display_title` in the row; full `session_key` moves to the Metadata tab (already there). Tooltip on truncate.
- NO AI summarization. The `summary` column is reserved for Phase 10+. Heuristic only for `display_title`.

**Out of scope**: AI summarization logic, summary backfill jobs, summary UI surfaces, any title-editing UI.

**Open questions**:
1. Heuristic for `display_title`: first user message vs. session_key tail vs. tool-specific (Claude Code has a `cwd` we could include)?
2. Migration story for existing imported sessions: backfill via rescan, lazy backfill on read, or one-shot migration command?

### Phase 7 — Transcript rendering overhaul (size: M-L)

**Goal**: Fix items 2 + 3 from the user's punch list:
- (Item 2) Parser warnings are currently surfaced loosely. Rule: "for un-important messages, don't hide them silently. You can collapse them, but allow user to zoom into it."
- (Item 3) Group consecutive same-type items. Multiple tool calls in a row should NOT each get a full card — they should be visually unified.

**Scope**:
- Enumerate all parser warning types (sub-task: spelunk `apps/frontend/src/features/sessions/parsers/` to list them).
- Design "collapse-with-inspect" UX: low-signal messages are collapsed by default with a chevron / "Show details" affordance; expanded reveals raw payload.
- Group consecutive same-type blocks (esp. consecutive tool calls). Reference: `github.com/OptimalCNC/agents-runner` (user hint; not authoritative, just inspirational).
- Update TranscriptView + parsers as needed. Stay within the existing token + hex budget.

**Out of scope**: Skim view changes (Phase 5 just landed it). Raw view changes (Phase 8). Backend parser changes (parsers live in frontend per Phase 5 architecture).

**Open questions**:
1. Is "consecutive same-type" purely visual grouping, or should we collapse the group itself by default and only show counts (e.g., "12 tool calls")?
2. What's "unimportant"? System messages? Tool-result echoes? Empty thinking blocks? Need a concrete taxonomy.

### Phase 8 — Raw view polish (size: S-M)

**Goal**: Raw tab currently renders JSONL line-by-line as plain text. Item 4: render JSON nicely. Reference: https://json-render.dev/docs.

**Scope**:
- Pretty JSON per line with collapse/expand, syntax highlight, copy buttons.
- Preserve streaming line cap (256 KB) and the existing caption.
- Evaluate `json-render.dev` as inline dep (cost vs. value vs. our existing hex/token invariants).

**Out of scope**: Transcript / Skim / Metadata changes. Streaming protocol changes.

**Open questions**:
1. Is json-render.dev a runtime dep or an inspiration? (Their bundle size + license + token-fit matter.)
2. Should "copy" copy the raw JSON line or the formatted version?

### Phase 9 — Job Center + execution model (size: L, foundational)

**Goal**: Replace synchronous Import / Rescan endpoints with a job model. Make all long-running ops idempotent, observable, and cancellable. Foundation for future Phase 10+ summarization.

**User's original framing** (from message):
- Import / rescan / summarize / re-summarize are all "jobs".
- Jobs are idempotent: re-submitting same job = no-op or returns existing.
- "Force re-summarize" exists to override idempotency.
- Job center is a UX surface to track all jobs.

**Coordinator's refinements** (what user is being asked to evaluate):
- Idempotency via params-hash, NOT via a special op. `summarize_session{ id, force: true }` has different params hash than `summarize_session{ id, force: false }` → naturally distinct jobs. No special-case code.
- Idempotency TTL: for ops whose inputs can change (e.g., re-import after a rescan with new data), tie the idempotency key to the source content hash. Otherwise import would never re-run after data drift.
- SSE (not WebSocket) for live status. Simpler, one-way, plays well with our Vite dev proxy.
- Explicit cancel API. Worker polls a cancel flag.
- Defer: job dependency graphs. Add only if needed.

**Proposed scope**:
- Backend: new `components/jobs/` crate. `jobs` table (id, kind, params_hash, status, created_at, started_at, finished_at, result_json, error_json, source_version_hash). Workers per kind. POST /api/v1/jobs, GET /api/v1/jobs, GET /api/v1/jobs/:id, DELETE /api/v1/jobs/:id (cancel), SSE /api/v1/jobs/:id/events.
- Frontend: `JobCenter` panel (slide-out from right pane edge? Modal? Inline?), `JobBadge` in action bar with running count.
- Refactor Import + Rescan to submit jobs. Direct synchronous endpoints retired (or kept as thin facades?).
- Job kinds in Phase 9: `import_sessions`, `rescan_sources`. NOT `summarize_session` — that lands in Phase 10.

**Out of scope**: Summarization jobs (Phase 10). Multi-user / multi-worker concurrency beyond what SQLite naturally serializes. Distributed queue (we're a single-binary backend).

**Open questions**:
1. New crate `components/jobs/` vs. fold into `raw-session-store`? Coordinator leans toward new crate (clean ownership).
2. SSE per-job vs. SSE single firehose channel for all jobs? Per-job is simpler, firehose is fewer connections.
3. Status transitions: pending → running → succeeded / failed / cancelled. Anything missing?
4. Worker model: tokio task per kind, single-threaded? Worker pool? Persistent state across backend restarts?
5. How to handle a backend crash mid-job? Resume on next boot vs. mark as `interrupted` and require re-submit?
6. Idempotency window: forever? 24h? Per-kind config? "Already imported" is forever; "rescan completed 5 minutes ago" might be replayable after 1 minute.
7. UI: where does Job Center live? Slide-out drawer (we just retired the modal Drawer for SessionDetail, so the pattern is gone but the implementation primitives may still be useful)? Fixed bottom bar? Separate route?
8. Optimistic UI: should clicking Import IMMEDIATELY add a job card to the JobCenter (optimistic) and only flip to error if the POST fails? Or wait for the server to acknowledge?
